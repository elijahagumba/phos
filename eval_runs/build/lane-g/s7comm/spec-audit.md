RFC 905 is a 1984 retyping of ISO DP 8073; X.224 (1995) / ISO/IEC 8073:1997 is the same standard as later published text, and it is cited below wherever it agrees with or corrects RFC 905.

## What the bytes do not allow

The lane must refuse each of these, and the refusal is the honest result, not a gap to fill.

1. **No `ProgramAct` from any S7 application byte.** No primary source names a job byte for read, write, download, upload or PLC stop. The wiring lane may construct a `ProgramAct` only from a job *this audit has signed*, and it has signed none. A missing citation refuses the act; the transport may still be judged met.
2. **No class other than 0 may be refused merely for being non-zero.** RFC 1006 §6 says only class-0 TPDUs are exchanged *in RFC 1006*, and that is signed. But Siemens labels its own ISO-on-TCP open-communication transport **"ISO-on-TCP according to RFC 1006 (Class 4)"** (11/2025 -AN, §8.2, Table 8-1), and RFC 2126 §4.2 adds class 2 over TCP. No primary source states which class an S7 COTP connection requests. A hard "class field != 0 → `BAD_HEADER_FIELD`" rule would manufacture false malformations on real Siemens traffic. Record the class octet; do not refuse on it alone.
3. **No refusal of a non-zero `reserved` octet.** RFC 2126 §6.10 is explicit: it "should be ignored on input".
4. **No refusal of a class-0 CR or CC that carries user data or extra parameters.** RFC 1006 §5 and its *Connection Establishment* clause permit exactly that "for testing purposes". Refusing it would refuse the connection setup S7 actually uses.
5. **No ED TPDU decoded through the X.224 class-1 ED layout.** RFC 1006's ED is a different shape (see D4). If ED is not decoded at all, that is an acceptable honest read; guessing the X.224 layout is not.
6. **No inference of a station, a peer role, or a program act from the TSAP bytes.** RFC 905 §13.3.4 says TSAP-ID is "identifier of the calling or called TSAP respectively" and defines no structure. Any meaning in a TSAP is an S7 convention, and no primary source publishes it.
7. **No name from port 102 alone.** IANA registers one service on 102 (`iso-tsap`, "ISO-TSAP Class 0"). That is a transport service, not S7, not MMS. The brief's *Foundation* rule already says 102 is not a port claim; this audit confirms the registry cannot support one.
8. **No length field may size an allocation before it is compared with the bytes present and with 65535.** RFC 1006 §6 gives 65535 as the TPKT ceiling and 65531 as the TPDU ceiling; X.224 §13.2.1 gives 254/255 for LI; RFC 905 §13.3 caps a CR at 128 octets. Those are the bounds. Nothing on the wire is trusted first.
9. **No claim that 65524 is a limit.** See D1.
10. **No detection claim of any kind.** Reach is not performance (ADR 0422). This lane says Atlas can read this language, and stops there.

## Defects and qualifications sent back to the engineer and the orchestrator

These are the misses. None of them is fixed by this auditor; none of them was edited into any dissector.

**D1 — 65524 is arithmetically wrong and must not become a bound.** RFC 1006 §6 says the 65535-octet packet "permits a maximum TPDU size of 65531 octets", which is right (65535 − 4), and then says it "permits a maximum TSDU size of 65524 octets", which is 65531 − 7. But X.224 §13.7.5 and RFC 905 §13.7.5 both say the DT user-data field is the negotiated TPDU size **minus 3 octets** in classes 0 and 1, because the class-0 DT header is 3 octets (LI, code, TPDU-NR/EOT). 65531 − 3 = **65528**. There is no erratum on RFC 1006 (the only one, ID 7890, is a typo in §7). The brief repeats 65524 as settled. **Recommendation:** the declaration records 65524 as "the figure RFC 1006 states, unreconciled against its own minus-3 rule and against X.224 §13.7.5", and codes **65535** (TPKT) and **65531** (TPDU) as the only two bounds. A 65524 constant in the source would be a fabricated limit. Note the useful cross-check that does hold: min=7 = 4-octet TPKT + 3-octet class-0 DT header, which independently corroborates constant E.

**D2 — claim C is right, but for a reason the brief does not give.** RFC 1006 does not *say* the reserved octet is unconstrained; it never defines it at all — the diagram names it, and no clause in the memo constrains its value. A reader who treats RFC 1006 as the only authority is relying on an omission. RFC 2126 §4.3 assigns it "Value: 0" and §6.10 then says it "should be ignored on input". So the dissector behaviour (record, never refuse) is **correct and now has positive normative support**, but the declaration should cite RFC 2126 §4.3 and §6.10 alongside RFC 1006 §6, and note that RFC 2126 is a Proposed Standard that updates, and never superseded, the Internet Standard RFC 1006.

**D3 — the DT code is not `1111 0000` in every format.** RFC 905 (1984) Table 8 prints `1111 0000`. X.224 (1995) Table 8 prints `1111 000y`, with "y (bit 1) Used to signal ROA if the request acknowledgement procedure has been agreed at connection establishment (classes 1, 3, 4 only)". Class 0 is unaffected, so this does not block the lane. It does mean a matcher written as `octet2 == 0xF0` is correct for class 0 and wrong for anything else on this port. Compare with the class recorded, not with a flat constant, or say in the docstring that the class-0 assumption is the reason the constant is safe.

**D4 — RFC 1006's ED TPDU has a different fixed part from X.224's.** RFC 1006 §6 gives the expedited TPDU as `| header length | code | credit | TPDU-NR and EOT | user data |` — code, credit and TPDU-NR/EOT in octets 2, 3 and 4, so **LI = 3**, and it says "After the credit field (which is always **ZERO on output and ignored on input**), there is one additional field prior to the user data." X.224 §13.8.1's class-1 ED is `|LI| ED | DST-REF | ED-TPDU-NR and EOT | Variable Part | User Data|` — **five** fixed octets, LI = 4, and no credit field. RFC 1006's ED is non-standard precisely because it borrows the DT shape and drops DST-REF. RFC 2126 §4.1.2 confirms: "The only difference between ED TPDU and DT TPDU is that the value used for the TPDU code is ED and not DT." Also signed: the expedited user data is **1 to 16 octets** ("Note that the TP specification limits the size of an expedited transport service data unit (XSDU) to 16 octets", RFC 1006 §6; RFC 2126 §4.1.2 repeats it). If the engineer decodes ED, it needs this layout; if not, the declaration should say ED is recorded and not decoded.

**D5 — LI's error test differs between the two texts.** RFC 905 §13.2.1: "If the length indicated **exceeds** the size of the NS-user data which is present, this is a protocol error." X.224 §13.2.1: "If the length indicated **exceeds or is equal to** the size of the NS-user data which is present, this is a protocol error." This lane does not need to resolve which governs: the brief's bar only asks that a class-0 DT whose LI disagrees with the TPKT length is `INCONSISTENT_COUNT`, and that a short header is `SHORT_HEADER`. Code LI > bytes-present as a refusal; do not code the equality case as a refusal on the strength of RFC 905 alone.

**D6 — claim G is the most dangerous line in the brief.** RFC 905 §8.2.2 is quoted correctly, and for bare ISO 8073 class 0 it is right. **It does not describe traffic on port 102.** RFC 1006 §5 opens: "The protocol specified by this memo is identical to the protocol for ISO transport class 0, **with the following exceptions**", and the first exception is "for testing purposes, initial data may be exchanged during connection establishment". Its *Connection Establishment* clause spells it out: "the connection request and connection confirmation TPDUs **may exchange initial user data, using the user data fields of these TPDUs**", and it also permits negotiating expedited data through "the 'Additional Option Selection' variable part" and a TPDU size through "the 'TPDU Size' variable part". X.224 (1995) §8.2.2 is itself wider than RFC 905, permitting "Transport-Selector, maximum TPDU size, **and preferred maximum TPDU size**". **So a dissector that refuses a CR/CC carrying user data, or carrying more than two parameters, will refuse lawful RFC 1006 connection setup.** The declaration must not cite G as a refusal rule. What it *can* keep from that clause is the genuine bound in §13.3: "The length of the CR TPDU shall not exceed 128 octets" (X.224 states the same, in §7 NOTES: "The length of the CR-TPDU does not exceed 128 octets (see 13.3)").

**D7 — claim H is signed, but the edition in the brief is one behind what could be seen.** The brief cites *11/2024, A5E03735815-AM, section 5.2*. Siemens' support host returns **403** to every direct request (`support.industry.siemens.com/cs/attachments/109826824/…` and `/dl/files/925/59192925/att_901175/v3/…`), and the search index's only target for `A5E03735815-AM` was itself a 403. What *is* reachable is Siemens' own cache host, `cache.industry.siemens.com`, for document **59192925** — the same document family, same order number stem:
- **11/2025, A5E03735815-AN**, 519 pages, §**5.2**, printed p.38 — contains the quoted sentence **verbatim**.
- **12/2014, A5E03735815-AD**, 98 pages, §**3.5**, printed p.23 — same substance: "ISO on TCP (according to RFC 1006) / **102 (4) TCP** / ISO-on-TCP protocol … S7 communication with ES, HMI, OPC server, etc."

The brief's **section number 5.2 matches the -AN layout**, not the 2014 edition's 3.5. That is good evidence the citation's shape is right and only the suffix is stale: -AM must be the edition between -AD and -AN, and its §5.2 will contain the same row. **Honest statement: I could not independently see -AM. I saw -AN, one edition later, containing the cited sentence word for word at the cited clause.** Marking this "cited-from-the-brief-not-independently-seen" would be too weak, since the text itself was seen in a Siemens document at the cited clause; the precise status is **signed against -AN, with -AM unreachable and presumed identical**. The declaration should cite what was actually read, or record both.

**D8 — I is unverified, and the gap is structural, not a search that fell short.** I could not find a primary source naming an S7 job byte, and I found positive evidence that none is published. The Siemens *Communication Function Manual* (11/2025 -AN) contains **zero** occurrences of "opcode", "PDU reference", "S7 header", "S7 frame", "telegram structure", "function code", `0x32` or `0x1A` as strings; it describes S7 communication entirely in terms of *instructions* (PUT/GET, BSEND/BRCV, USEND/URCV) and configured connections. It states outright that S7 communication is "vendor-specific communication between SIMATIC CPUs (**not an open standard**)" (§9, printed p.161). The other Siemens text I could reach, *SIMATIC NET S7 Programming Interface* (C79000-G8976-C077), is an **API** manual — `s7_multiple_read_req()`, `s7_multiple_write_req()`, job identifiers and confirmation handlers — and defines no wire octets either. **Consequence for the verdict:** this refusal cannot be lifted by looking harder. It is lifted only by Siemens publishing the frame format or licensing a specification. That should be written in ADR 0348 and in the refusal register, because a future session will otherwise re-run this search. No blog, Stack Overflow answer, protocol cheat-sheet, Wiki, or dissector source was accepted as evidence at any point in this audit.

## Verdict of this audit

The application is not.** Constants A–F and H stand on primary text — A, B1–B4, D1–D3, D5–D8, E and F without qualification; B5, C, D4, G and H with the qualifications recorded in their cells and expanded as D1–D7.
