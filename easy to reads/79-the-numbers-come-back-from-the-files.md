# 79 — The numbers come back from the files

Version 1 has a criterion, A7, that sounds modest and is not: *one command
regenerates every version-1 number, and someone outside the project has run it.*
A number you cannot rebuild is a number you are asking people to take on trust.

Until today the command mostly checked. It rebuilt one table from the recordings
and then compared the rest against fingerprints — which catches an edit, but would
not catch a number that was never right in the first place.

Now four of the five records are rebuilt from the recordings themselves: the
results table, the comparison against the published method, and both consistency
records. The command opens the plant recordings, scores them again, and compares
what comes out with what was written down. A disagreement would have been the
answer, and we said so in writing before running it.

Everything matched. All ten rows came back intact — fifty-four separate digits and
five file fingerprints. One detail is worth naming: the grouped half of the results
table used to be a copy. We had recomputed the plain rows and, honestly, reprinted
the grouped ones, and said so at the time. Those are now rebuilt too, and they
match: 5 of 58 against the other method's 10 on one dataset, 5 of 52 against 6 on
the next.

Nothing was written during the run. The old result log still has exactly 185 rows.

And A7 still fails, for two reasons we wrote down before looking.

The first is a genuine collision between two of our own rules. Three headline
numbers — 646.58, 18.72, 0.104 — are frozen: never overwritten, and any new result
has to take a new name. That rule exists so nobody can quietly improve history. But
it also means those three cannot be *regenerated*; recomputing them would create
different numbers standing beside them, not the same ones again. So "every number"
cannot be satisfied while the freeze holds. We could have narrowed the sentence to
the four records that do rebuild and called it a pass. We did not, because a
criterion rewritten after the measurement it judges is not a criterion.

The second is simpler: nobody outside the project has run it yet.

So the count stays at 8 of 12. The honest version of today is that the command got
substantially better and the criterion it serves still fails.
