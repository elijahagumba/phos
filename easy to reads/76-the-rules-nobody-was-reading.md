# 76 — The rules nobody was reading

PHOS has a long list of things an assistant working on it must not do. Do not quietly rewrite a
measured number. Do not mix two kinds of result that were measured apart. Do not open the files held
back for the final test. Do not call something finished while the public pages still describe
yesterday. That list is the product, really: the discipline is what makes the numbers worth
anything.

The list was written down in six files. One of them opened by telling the reader to paste it in at
the start of every session.

Nobody was pasting it. One of the two tools used to build PHOS reads those files by itself. The
other one — the one that has done most of the work — never looked in that folder, and the file that
would have told it to was switched off in the project's settings, by an earlier decision that said
the rules lived elsewhere. So for a long run of working sessions, the rules existed and did not
arrive. Nothing was being enforced; it was being remembered, which is not the same thing.

Two consequences had already appeared. The ten short role descriptions — the researcher, the writer,
the one that guards the numbers — each repeated a few of the frozen figures from memory, and one of
them named a stage of work that had finished weeks earlier. A number copied into a second place is a
number that will eventually disagree with itself.

And the project's progress file, the one every session is told to read first and update last,
recorded a date two months stale. It was a counter that nothing counted. The reason turned out to be
a test: the test that protects the frozen numbers also pinned the counter to one exact value, so any
honest advance would have turned the tests red. The only way to keep the tests green was to leave
the file wrong.

Four things changed. The rules now load themselves, from one copy, into both tools. The role
descriptions keep their job and their method and quote no figures at all — they point at the file
that holds them. A small script moves the counter, reading the decision records, the result log and
the version history to work out where things stand, and refusing to touch anything frozen. And the
test was split: it still pins every frozen number and every closed stage, and it no longer pins the
counter.

Nothing was measured here, and no result moved. What changed is that the rules now reach the thing
that was supposed to be following them, and the progress file can be true. There are also five
small warnings that fire before the five most expensive mistakes — running a measurement nobody
declared first, writing to the frozen result log, opening the held-back files, editing outside your
own patch of the code, and shipping a change without updating these pages. For now every one of them
only warns and lets the work continue. Turning them into refusals is a single switch each, and none
of them has been turned.
